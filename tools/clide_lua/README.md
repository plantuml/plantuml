# tools/clide_lua

[Lua](https://github.com/plantuml/clide/blob/main/LUA.md) scripts for
[clide](https://github.com/plantuml/clide), the semantic Java navigation tool.
They run inside the clide daemon, which has already loaded the project.

See also [`CLAUDE-FIXING-ISSUES.md`](../../CLAUDE-FIXING-ISSUES.md) (section 1.3)
for how to set clide up and use it on this repository.

## check_assert_guard.lua

Checks that every `assert` in the source code is guarded by `TeaVM.a()`, so that
it is eliminated from the JavaScript generated by TeaVM (see the javadoc of
`net.sourceforge.plantuml.teavm.TeaVM#a()`).

### Forms recognized as guarded

```java
if (TeaVM.a()) assert x;      // single line

if (TeaVM.a())                // guard alone on line L-1
    assert x;                 // assert on line L
```

### Usage

1. Build clide with `ant` (never `gradlew`: it needs network access). This
   produces `clide.jar`, which must sit next to `start_clide.py`:

   ```
   git clone --depth 1 https://github.com/plantuml/clide
   cd clide && ant
   ```

2. Start the daemon on PlantUML, once:

   ```
   python3 start_clide.py /path/to/plantuml
   ```

   It launches the daemon detached, prints its boot trace, and waits until it
   prints a line ending with `... is ready to use.`. Running the same command
   again is safe: it recognizes the running daemon and starts nothing further.
   (Do not run `java -jar clide.jar` directly any more.)
3. Run the script against that daemon:

   ```
   python3 clide.py --lua tools/clide_lua/check_assert_guard.lua /path/to/plantuml
   ```

   The project path may be omitted: `clide.py` defaults to the last one
   `start_clide.py` was pointed at.

A script blocks the daemon while it runs (it serves one client at a time), so do
not open a second client before it finishes.

### Output

A summary line, then one `NOT GUARDED  path:line: text` line per unguarded
`assert` (`NOT GUARDED (block guard)` when the previous line opens a block
`if (TeaVM.a()) {`: guarded, but not in the repository's form). `if (TeaVM.a())` guards whose next line is not an `assert` are listed
separately (`ORPHAN GUARD`).

Example (repository state on 2026-09-29):

```
237 assert(s) examined: 95 guarded inline, 65 guarded on the previous line, 77 NOT GUARDED  (86 lines ignored: comments/strings)
```

### How it works

`search_regex` finds the candidate lines (all `assert`s, all standalone guards);
`read_lines` then reads what surrounds each one: the line before an `assert`
(is it a guard?) and the line after a guard (is it an `assert`?). clide's Lua has
no `io`, and `search_regex` only returns the matching line, so without
`read_lines` the script had to cross-reference the two searches by line number.
The result cap is raised to 10000 (the maximum), and the script stops with an
error if a result is still truncated.

This needs a clide that has the `read_lines` command.

### Limits

- Only the line before an `assert` is looked at. A block guard is recognized and
  named, not accepted; a guard separated from its `assert` by a comment or a blank
  line is reported as not guarded.
- The script does not know which files TeaVM actually compiles. An unguarded
  `assert` in code TeaVM never reaches (for example `argon2`) is reported anyway.
- `assert`s inside comments or strings are ignored heuristically (a `//` or an
  odd number of double quotes before the word).

## vega_check.lua and vega_update.lua

Drive the Vega non-regression suite (`test.vega.VegaTest`) from clide, and tell
which reference files (`src/test/resources/vega/**`) the run touched. They need a
clide with `snapshot`/`changed_since`; `vega_update.lua` also needs `set_test_env`.

```
python3 clide.py --lua tools/clide_lua/vega_check.lua  /path/to/plantuml
python3 clide.py --lua tools/clide_lua/vega_update.lua /path/to/plantuml
```

- **`vega_check.lua`** runs the suite as it is. It prints the counts, one line per
  failing case, and the reference files the run *wrote anyway*: `VegaTest`
  creates a reference that does not exist and the case passes silently, so a
  forgotten `.svg` only shows here (`WRITTEN [created]`). Nothing is regenerated.
- **`vega_update.lua`** runs it with `VEGA_FORCE_WRITE=true`, then lists the files
  whose content moved with their md5 before and after (the comparison is on
  content, not on dates: a reference rewritten identically is not listed). The
  setting is always reset afterwards, even if the run fails.

The rule: run `vega_check.lua` first, read what fails, and only then
`vega_update.lua`. What it lists must be what you expected to move. It does not
judge the new references and does not commit; look at each moved one before
keeping it (a reference that moves by accident is a regression that the rewrite
would otherwise have erased).

`vega.json`, `vega-summary.txt` and `vega-summary.md` are rewritten by every run
and are never listed; `git checkout` them unless you mean to commit them.

Limits: a moved reference is told by its md5, not judged; to see the images,
render the old and new `.svg` yourself. The four cases marked `allow-failure` are
reported as skipped, not failed. A whitespace-only change after `</svg>` does not
make a case fail (the comparison cleans the SVG) but does change the md5, so
`vega_update.lua` lists it.

## list_could_be_private.lua

Lists the `public` methods that could be `private`: those whose every real usage
(as jdtls sees it) stays inside the type that declares them. A method that is
never called at all is listed too, marked `(never called)`: it is as narrowable
as one used only from inside its own type (and is often better deleted).

```
python3 clide.py --lua tools/clide_lua/list_could_be_private.lua /path/to/plantuml
```

(the daemon must be running, see above). Output: one line per candidate,
grouped by file, then a summary line.

```
  src/main/java/net/sourceforge/plantuml/abel/Link.java:320: Link.getWeight  (never called)
  ...
23 type(s) examined: 13 public method(s) could be private, 0 more cannot be narrowed (implement/override)
```

### How it works

`list_could_be_private` takes one type at a time. The script finds every type
declaration (top-level and nested) with `search_regex`, computes the position of
its name, and calls the command on each one (inside `pcall`: a type that fails is
reported as `FAILED`, the audit goes on). A method that implements or overrides
something cannot be narrowed: it is only counted, unless `SHOW_OVERRIDES` is set
to `true` at the top of the script.

### Traces

The script prints as it goes: `[i/N] path:line Type` **before** each type is
examined (the last one seen is the one that was running), and each
`candidate:` / `FAILED` line as soon as it is known, then the sorted report at
the end. If the client gives the prompt back before the end (the connection
dropped while the daemon goes on running the script), what was printed so far
is a partial result, and the last `[i/N]` line says where the daemon was.
`TRACE_EVERY` (top of the script) prints one progress line every N types;
`0` turns the progress lines off.

### Cross-check: "never called" can be wrong

`(never called)` means that jdtls found no reference at all. While jdtls has not
finished indexing the project that is simply what it answers for every method:
`start_clide.py` can print "ready" before the indexing is over on a project of
PlantUML's size, and a script started right then lists callable methods as
unused. Each `(never called)` candidate is therefore also looked for as plain
text (`name(`) in `src/main/java`, and marked `SUSPECT` when it appears in
another file. A name shared with an unrelated class gives a harmless false
alarm; many `SUSPECT` lines mean the index was not ready: wait a few minutes
after starting the daemon and run the script again. `CROSS_CHECK = false`
turns it off.

### Limits

- It is slow: one `find_reference` per public method, so a run on the whole of
  `src/main/java` takes a long time. Set `ROOT` at the top of the script to one
  package for a quick run.
- Only usages jdtls can see are counted. Reflection, serialization hooks and
  anything discovered by name are invisible: check each candidate before
  narrowing it.
- `public` is read as text off the declaration line (see clide's
  `CLAUDE.md`, known limitations).
- The script only reports; it changes nothing.
